# 1. 观察预处理结果
使用命令`gcc -E a.c`发现预处理后的代码比源文件多了许多stdio.h库的宏定义以及函数声明。
# 2. 寻找头文件
通过命令`man gcc | grep -- -I`得知-I选项的作用是编译时的添加新的include头文件搜索路径，如果在本地include文件夹定义stdio.h，使用命令`gcc -I ./include -E a.c`展开的预处理文件将覆盖系统头文件成为自定义的头文件内容。
# 3. 对比gcc和riscv64-linux-gun-gcc的预定义宏
通过命令:
```bash
diff -y --width=120 --suppress-common-lines \
<(echo | gcc -dM -E - | sort) \
<(echo | riscv64-linux-gnu-gcc -dM -E - | sort)
```
对比发现两种不同目标平台对同一C标准库头文件的预处理展开结果有差异，差异主要体现在平台特有宏定义、浮点数精度、类型字长上。
# 4. 通过man clang了解编译过程
查阅clang手册得知编译分为以下几个阶段（个人理解未必准确）：  
1. 驱动阶段：主要是编译全流程的配置和控制操作
2. 预处理：将源码中的头文件、编译预处理命令、宏替换操作全部展开，生成.i文件
3. 词法和语法分析: 将.i文件的字符串解析并生成Token,语法的错误和警告检查都在该阶段完成，生成抽象语法树AST；
4. 中间代码IR生成与优化: 将AST抽象语法树转化为平台无关的中间码IR code，根据优化等级采取不同的编译优化策略，例如常量计算，死代码消除、循环加速等各种操作，减少代码在运行时的开销，最后输出汇编码.s文件
5. 汇编器：将.s文件做一些简单的翻译替换，分配寄存器和伪指令展开，转化成最终的平台目标码.o文件
6. 链接器：将所有源码生成的.o文件进行整合，符号表解析、重定位、链接成一个可执行程序。
# 5. 对比编译优化结果
通过命令:
```bash
diff -y --suppress-common-lines \
<(gcc -Q --help=optimizers -O0) \
<(gcc -Q --help=optimizers -O1)
```
对比发现-O1开启了更多优化策略，高等级优化对应更少的IR代码
```bash
diff -y --suppress-common-lines \
<(clang -S -emit-llvm -O0 a.c -o /dev/stdout) \
<(clang -S -emit-llvm -O1 a.c -o /dev/stdout)
```

# 7. 查看riscv64目标文件/可执行文件的反汇编结果
使用命令对比目标文件反编译结果与编译器汇编结果：
```bash
riscv64-linux-gnu-gcc -c a.c  # gcc生成目标文件a.o
llvm-objdump-18 -d a.o  # 对目标文件进行反汇编
riscv64-linux-gnu-gcc -S a.c -o -  # gcc生成汇编文件重定位到输出

diff -y --width=120 --suppress-common-lines \
<(llvm-objdump-18 -d a.o) \
<(riscv64-linux-gnu-gcc -S a.c -o -)
```
编译器汇编结果有许多字符和未解析的函数入口地址，反汇编结果几乎都是机器码，函数入口不再是字符而解析成了真正的地址。

# tail. 随笔记录
既然C语言标准的未定义行为如此致命，为什么C99标准不明令禁止，而是留有余地给编译器来处理这些未定义行为。  
这是C语言设计的核心理念之一：在性能、可移植性和安全性之间做出的根本性权衡。这也是C标准的初衷：它让你拥有了极致地操作硬件底层的自由，同时也赋予了你制造灾难性Bug的自由。  
运行时环境 = ISA+OS+库函数，而ABI的本质就是运行时环境的接口规范
